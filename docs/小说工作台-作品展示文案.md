## 02 / 09｜项目背景

**Project background**

# 长篇创作如何保持连贯？

围绕市场现状、作者任务与产品机会，明确产品需要解决的核心问题。

### 核心判断

**长篇创作需要稳定管理跨章节上下文，明确控制生成过程，并把每次结果沉淀为可继续使用的项目资产。**

### 01 / MARKET｜市场调查

现有通用 AI 写作产品主要围绕对话和单次生成设计，能够处理短内容，但缺少面向长篇项目的持续管理能力。

- **生成同质化：**模型能力可替换，单纯增加一个聊天入口难以形成产品价值。
- **长篇缺工具层：**跨章节设定、人物关系、伏笔和版本仍主要依赖作者手工维护。
- **本地化有价值：**小说原稿、API 配置与创作资产需要隐私、可迁移和可自主选择模型。

**机会：做模型之上的“创作流程与资产层”**

### 02 / AUDIENCE｜目标用户

核心用户是已经进入项目制创作、需要长期维护复杂设定和章节连续性的长篇作者。

- **核心用户：**长篇网文 / 小说作者、设定控、重度 AI 辅助写作者。
- **关键任务：**原创从零初始化；同人先提取原著特征；之后逐章生成与校验。
- **主要焦虑：**设定遗忘、角色失真、流程失控、失败覆盖、结果无法继续复用。

**需求：连续记忆 + 明确步骤 + 用户最终控制权**

### 03 / ANGLE｜产品切口

产品聚焦项目资料到章节正文之间的生成链路，以本地工作流组织上下文、步骤和文件，并保持模型选择的开放性。

- **步骤化：**初始化与章节分别拆解，每步只生产一种可检查资产。
- **文件化：**JSON 供程序读取，Markdown / TXT 供作者查看、编辑和版本管理。
- **可恢复：**撤回、重试、失败保留、用量记录与刷新恢复共同构成过程证据。

**定位：本地 AI 长篇创作工作台**

市场缺口 → 长篇作者任务 → **工作流 + 本地资产**

## 03 / 09｜页面设计

**Interface design**

# 三栏如何组织创作流程？

三栏分别承载项目上下文、当前操作和正式产物，让作者在一个画面内完成执行、检查与修改。

### 01｜项目始终可见

左侧持续显示当前小说、卷、章节与其他项目，避免切换任务后失去归属感。

### 02｜流程集中呈现

中间区域同时呈现用户补充、生成结果、失败信息与下一步，让执行记录自然可读。

### 03｜文件直接交付

右侧直接打开、预览和编辑 Markdown / TXT；生成结果不被锁在聊天消息里。

页面标注：

- 1 项目导航
- 2 步骤式对话
- 3 文件工作区

**信息架构：**小说 → 卷 → 章节 → 资产

**交互状态：**生成 / 完成 / 失败 / 重试

## 04 / 09｜初始化流程

**Flow 01 · Initialization**

# 如何建立全局创作记忆？

每一步只负责一种正式资产。用户可补充信息，系统将完整上下文持续累积。

实机状态 / 同人项目原著提取与初始化资产栏

### 九类资产承接全局设定

原创项目从小说资料判别开始；同人项目先完成原文统计、词频、文风与词库提取，再进入同一条初始化链路。

- **01｜资料判别 → 小说简介**：角色 + 剧情门禁
- **02｜世界观 → 语言风格**：规则与表达
- **03｜角色名单 → 角色卡 → 关系卡**：人物网络
- **04｜剧情书 → 剧情卷 → 信息账本**：全局推进

## 05 / 09｜单章生成

**Flow 02 · Chapter generation**

# 单章生成：把一次创作，<br>拆成六个可检查节点。

正文只在上下文快照完成后生成；校验集中在最后一步，避免过早门禁打断创作。

### 带证据链的章节产物

每个节点读取明确资产、写入明确文件，并保留模型、token、耗时和错误；正文与提示词都可从右侧文件区回看。

#### INPUT GATE｜先确认本章信息

至少包含已知角色与具体因果推进。

#### CONTEXT｜完整上下文不截断

世界观、角色、关系、剧情和上一章结尾共同参与。

#### OUTPUT｜文件化产物

锚点、配置、台词、快照、正文、校验报告分别落盘。

#### CONTROL｜撤回 / 重试 / 下一步

用户决定何时认可结果并继续。

章节流水线：

- **01｜强制锚点**：锁定事实
- **02｜章节配置**：结构选择
- **03｜关键台词**：角色口吻
- **04｜提示词快照**：冻结上下文
- **05｜正文**：正式落盘
- **06｜校验验收**：格式与语义

## 07 / 09｜过程追溯

**Traceability & recovery**

# 生成失败如何定位恢复？

错误不会覆盖正式产物；消耗仍会计入项目，用量与执行事实保持一致。

### 每次生成都有完整记录

工作台把“发生了什么”留在界面和本地日志中：哪一步失败、使用哪个模型、输入输出多少、耗时多久，以及用户接下来可以做什么。

- **01｜失败不覆盖：**只有通过校验的结果才写入正式资产。
- **02｜用量可回填：**workflow-state 与执行日志共同保存统计。
- **03｜网络自动重试：**429、5xx 与瞬时网络错误最多退避 3 次。
- **04｜过程可恢复：**刷新后恢复聊天、当前步骤与文件状态。

## 08 / 09｜技术架构

**Technical architecture**

# 本地架构如何支撑流程？

前端负责操作与呈现；Node 处理文件和接口；Python 负责工作流、上下文与模型调用。

### 普通文件承载全部资产

数据以小说项目文件夹为边界。结构化资产同时保存 JSON 与 Markdown：程序读取源文件，用户查看可读版；章节正文、提示词和运行记录都能被外部工具直接管理。

技术栈：

- Vanilla HTML / CSS / JS
- Node.js HTTP
- Python 3
- OpenAI-compatible API
- Local filesystem

**关键路径：**用户输入 → REST 接口 → Python 工作流 → LLM / 本地步骤 → 格式校验 → JSON + Markdown / TXT → 前端恢复状态。

### LAYER 01｜Web 工作台

项目导航、步骤式对话、流程控制、文件预览与结构化编辑

`web/`

### LAYER 02｜本地服务

静态资源、项目与文件接口、设置、工作流进程调度

`server.mjs`

### LAYER 03｜工作流引擎

步骤定义、上下文组装、模型配置、格式校验与执行记录

`Python`

### LAYER 04｜小说项目资产

知识库 / 词汇库 / 剧情 / 提示词 / 正文 / 运行记录

`filesystem`
