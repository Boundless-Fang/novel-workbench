02 / 09

Project background

为什么是“工作台”，
而不是另一个写作聊天框？

从市场形态、真实用户任务和产品机会三个层次，确定项目的设计边界。

核心判断 长篇创作的竞争点已经不只是“能不能生成”，而是能否管理跨章节上下文、控制过程，并把结果沉淀为长期资产。
01 / MARKET

市场调查

通用 AI 写作产品大多以“对话 + 单次生成”为核心，适合短内容，却很难承担一部长篇小说持续数月的创作管理。

  • 生成同质化模型能力可替换，单纯增加一个聊天入口难以形成产品价值。
  • 长篇缺工具层跨章节设定、人物关系、伏笔和版本仍主要依赖作者手工维护。
  • 本地化有价值小说原稿、API 配置与创作资产需要隐私、可迁移和可自主选择模型。
机会：做模型之上的“创作流程与资产层”
02 / AUDIENCE

目标用户

核心用户不是偶尔让 AI 续写一段的人，而是已经进入项目制创作、需要持续维护复杂设定的长篇作者。

  • 核心用户长篇网文 / 小说作者、设定控、重度 AI 辅助写作者。
  • 关键任务原创从零初始化；同人先提取原著特征；之后逐章生成与校验。
  • 主要焦虑设定遗忘、角色失真、流程失控、失败覆盖、结果无法继续复用。
需求：连续记忆 + 明确步骤 + 用户最终控制权
03 / ANGLE

产品切口

不做内容社区、不做发布平台，也不绑定单一模型；只解决从项目资料到章节正文之间最复杂、最容易失控的生成链路。

  • 步骤化初始化与章节分别拆解，每步只生产一种可检查资产。
  • 文件化JSON 供程序读取，Markdown / TXT 供作者查看、编辑和版本管理。
  • 可恢复撤回、重试、失败保留、用量记录与刷新恢复共同构成过程证据。
定位：本地 AI 长篇创作工作台
市场缺口→长篇作者任务→工作流 + 本地资产
03 / 09

Interface design

一个画面，容纳创作、
流程与文件。

三栏不是信息堆叠，而是把“项目上下文—当前动作—正式产物”保持在同一视野。

项目永远在场

左侧持续显示当前小说、卷、章节与其他项目，避免切换任务后失去归属感。

对话承担流程

中间区域同时呈现用户补充、生成结果、失败信息与下一步，让执行记录自然可读。

文件就是交付物

右侧直接打开、预览和编辑 Markdown / TXT；生成结果不被锁在聊天消息里。

1项目导航
2步骤式对话
3文件工作区
信息架构：小说 → 卷 → 章节 → 资产交互状态：生成 / 完成 / 失败 / 重试

05 / 09

Flow 02 · Chapter generation

单章生成：把一次创作，
拆成六个可检查节点。

正文只在上下文快照完成后生成；校验集中在最后一步，避免过早门禁打断创作。

生成的不是一段文字，
而是一份带证据链的章节。

每个节点读取明确资产、写入明确文件，并保留模型、token、耗时和错误；正文与提示词都可从右侧文件区回看。

INPUT GATE先确认本章信息

至少包含已知角色与具体因果推进。

CONTEXT完整上下文不截断

世界观、角色、关系、剧情和上一章结尾共同参与。

OUTPUT文件化产物

锚点、配置、台词、快照、正文、校验报告分别落盘。

CONTROL撤回 / 重试 / 下一步

用户决定何时认可结果并继续。

01强制锚点锁定事实
02章节配置结构选择
03关键台词角色口吻
04提示词快照冻结上下文
05正文正式落盘
06校验验收格式与语义

Key interactions

把复杂度藏进规则，
把选择留给创作者。

新建小说、流程预设与结构化配置不需要各占一页，但共同构成“可控”的产品体验。

三个轻入口，
控制一条重流程。

项目先选择原创 / 同人；设置中决定需要哪些初始化与章节步骤；具体章节配置只允许从受控选项中选择。自由输入与结构约束各司其职。

01新建小说：建立项目边界与创作类型
02流程预设：按创作习惯裁剪步骤
03选择式配置：避免模型静默生成非法枚举
07 / 09

Traceability & recovery

失败不是终点，
而是一条可定位的记录。

错误不会覆盖正式产物；消耗仍会计入项目，用量与执行事实保持一致。

让每次生成都
可以解释，也可以回来。

工作台把“发生了什么”留在界面和本地日志中：哪一步失败、使用哪个模型、输入输出多少、耗时多久，以及用户接下来可以做什么。

01失败不覆盖只有通过校验的结果才写入正式资产。
02用量可回填workflow-state 与执行日志共同保存统计。
03网络自动重试429、5xx 与瞬时网络错误最多退避 3 次。

08 / 09

Technical architecture

简单的本地架构，
承载复杂的生成流程。

前端负责操作与呈现；Node 处理文件和接口；Python 负责工作流、上下文与模型调用。

没有黑盒数据库，
每个产物都是普通文件。

数据以小说项目文件夹为边界。结构化资产同时保存 JSON 与 Markdown：程序读取源文件，用户查看可读版；章节正文、提示词和运行记录都能被外部工具直接管理。

Vanilla HTML / CSS / JSNode.js HTTPPython 3OpenAI-compatible APILocal filesystem
关键路径：用户输入 → REST 接口 → Python 工作流 → LLM / 本地步骤 → 格式校验 → JSON + Markdown / TXT → 前端恢复状态。
