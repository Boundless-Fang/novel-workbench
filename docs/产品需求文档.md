## 1. 需求概述

### 1.1 需求背景

长篇小说创作不是一次性生成任务。作者需要在数十至数百章中持续维护世界规则、人物状态、关系变化、剧情推进、伏笔和语言风格。通用对话式 AI 可以生成局部文本，但对“资料如何沉淀、上下文如何复用、过程如何恢复、结果如何验收”的支持有限。

小说工作台选择在模型之上增加一层本地创作流程：将初始化、章节生成和校验拆成明确步骤，把每一步的正式结果保存为普通文件，并记录流程状态和模型调用事实。产品不替代作者决策，也不承担内容发布，而是降低长篇 AI 辅助创作的上下文管理和过程失控风险。

需求来源包括：项目作者的创作流程观察、对长篇生成任务的拆解，以及现有原型与工程实现。目标用户、痛点强度和付费意愿目前均为产品假设，仍需真实用户研究验证。

### 1.2 问题陈述

| 问题 | 对用户的影响 | 当前证据与状态 |
| --- | --- | --- |
| 设定、角色和剧情分散在长对话中 | 后续章节容易遗漏事实，用户需要反复复制资料 | 已通过文件化知识库和上下文组装解决实现问题；真实使用收益待验证 |
| 一次生成混合多个任务 | 错误难定位，用户无法只重做某个环节 | 已拆分初始化与章节步骤，并提供撤回、重试和下一步 |
| 生成结果只存在于聊天消息 | 难以编辑、迁移、版本管理和复用 | 正式资产落盘为 JSON、Markdown 或 TXT |
| 模型失败可能导致进度不清或结果覆盖 | 用户无法判断消耗、失败位置和恢复方式 | 已记录模型、token、耗时、错误；写入前有格式门禁 |
| 同人创作需要先理解参考文本 | 手工提取文风、词频和专属词汇成本高 | 已提供五步提取链路；真实模型质量仍需验证 |
| 长篇跨章一致性难以持续维护 | 已发生的事实和人物状态可能与新正文冲突 | 当前有校验报告，但验收后的资产增量更新尚未实现 |

### 1.3 产品目标

| 目标编号 | 产品目标 | 用户结果 |
| --- | --- | --- |
| G1 | 建立可持续累积的小说项目资产 | 用户不必在每章重新整理全部设定 |
| G2 | 将复杂生成拆成可检查、可重试的步骤 | 用户能定位问题并只重做当前步骤 |
| G3 | 让正式结果可追溯、可编辑、可迁移 | 用户拥有普通文件，不被锁在对话界面中 |
| G4 | 在正文生成前冻结明确上下文，在生成后集中校验 | 降低设定遗漏、角色失真和格式问题 |
| G5 | 支持原创与同人两条入口，并允许选择模型 | 用户可按创作类型和成本偏好配置流程 |

## 2. 需求范围

### 2.1 本期范围

本期交付一个单机、单用户、本地网页工作台，包含：

- 原创 / 同人项目的创建、重命名、删除、切换和本地目录管理；
- 同人参考文本上传，以及原文统计、高频词、原文风格、正向词库、专属词库五步提取；
- 初始化资料判别与九类全局资产生成；
- 章节信息判别与“锚点 → 配置 → 台词 → 提示词快照 → 正文 → 校验”流程；
- 全局资产更新、正文改写草稿和章节评分；
- 标准、自动和部分手动交互能力；
- 本地文件预览 / 编辑、流程状态恢复、执行记录与 token 用量统计；
- 多个 OpenAI 兼容模型提供方及分步骤模型覆盖；
- 一键启动、统一测试入口和本地作品展示。

### 2.2 非本期范围

- 云端账号、跨设备同步、多人实时协作和权限体系；
- 小说社区、投稿、发布、排版、版权交易和商业化结算；
- 正文校验通过后自动更新剧情卷、世界观、语言风格、角色卡、关系卡和信息账本；
- 自动版本快照、Git 自动提交、回收站和跨设备备份；
- 覆盖全部步骤的手动结构化表单；
- 模型效果承诺、内容事实正确性承诺和版权合规代审；
- 移动端适配与生产级公网部署。

### 2.3 优先级定义

| 优先级 | 定义 |
| --- | --- |
| P0 | 核心链路不可缺少；缺失时无法完成从项目到章节的主要任务 |
| P1 | 显著提升控制、恢复或效率；缺失时仍可完成核心链路 |
| P2 | 体验优化或后续扩展，不阻塞当前演示与验证 |

## 3. 用户与业务场景

### 3.1 目标用户

| 用户 | 特征 | 核心任务 | 验证状态 |
| --- | --- | --- | --- |
| 长篇网文 / 小说作者 | 持续写作，有多章、多角色和复杂设定 | 管理全局资料并逐章生成 | 假设，待访谈与任务测试 |
| 设定型创作者 | 重视世界规则、角色关系和伏笔 | 先结构化资产，再进入正文 | 假设，待验证 |
| 重度 AI 辅助写作者 | 使用多个模型，关注成本和可控性 | 分步骤选模、重试、查看消耗 | 假设，待验证 |
| 同人作者 | 需要参考原著的文风与专属词汇 | 上传原著、提取特征、生成衍生内容 | 假设，待验证 |

间接利益相关者包括作品编辑、测试者和后续维护者，他们需要从普通文件和执行记录中复核产物。当前产品为单用户本地工具，不单独提供管理角色。

### 3.2 核心场景

1. 原创初始化：用户只有角色、背景和剧情梗概，希望建立可持续使用的小说知识库。
2. 同人初始化：用户上传 TXT / Markdown 原著，希望先获得统计、文风和词库，再进入与原创相同的初始化流程。
3. 逐章生成：用户提供本章角色与因果推进，依次确认锚点、配置、台词和上下文快照，生成正文并校验。
4. 局部返工：某一步结果不满意，用户撤回或重试，不希望重跑整个项目。
5. 中断恢复：浏览器刷新或模型失败后，用户希望恢复当前项目、章节、对话、步骤和用量。
6. 全局资产修订：创作中发现设定变化，用户希望单独更新简介、世界观、角色卡等资产。

### 3.3 核心业务流程

原创流程：

```text
新建原创项目
→ 输入小说资料
→ 角色 / 剧情门禁
→ 简介 → 世界观 → 语言风格 → 角色名单
→ 批量角色卡 → 批量关系卡 → 剧情书 → 剧情卷 → 信息账本
→ 完成初始化
→ 新建章节
→ 章节信息门禁
→ 锚点 → 配置 → 台词 → 提示词快照 → 正文 → 校验
→ 用户通过 / 撤回 / 重试
→ 下一章
```

同人流程：

```text
新建同人项目并上传原著
→ 原文统计 → 高频词 → 原文风格 → 正向词库 → 专属词库
→ 进入原创项目同款初始化与章节流程
```

失败恢复流程：

```text
步骤执行失败
→ 保留既有正式文件、用户输入和步骤位置
→ 展示错误、模型、token、耗时
→ 用户修改输入 / 模型后重试，或撤回到上一步
```

## 4. 产品方案

### 4.1 整体方案

产品采用“一个工作台、两条主流程、四层资产”的方案：

- 一个工作台：左侧管理项目 / 卷 / 章节，中间承载步骤式对话，右侧查看和编辑文件；
- 两条主流程：初始化负责全局资产，章节流程负责单章资产和正文；
- 四层资产：知识库与剧情、章节提示词、正文与草稿、运行记录；
- 模型层可替换：统一通过 OpenAI 兼容接口调用，允许分步骤覆盖提供方、模型和思考强度。

### 4.2 信息架构

```text
小说工作台
├─ 项目
│  ├─ 原创项目
│  └─ 同人项目
├─ 全局资产
│  ├─ 提取 / 知识库 / 词汇库
│  └─ 剧情书 / 剧情卷
├─ 章节资产
│  ├─ 锚点 / 配置 / 台词 / 提示词快照
│  └─ 正文 / 草稿 / 评分 / 校验报告
└─ 系统能力
   ├─ 模型与流程设置
   ├─ 文件预览与编辑
   └─ 状态、对话、执行记录与用量
```

### 4.3 原型与交互规则

原型以可运行页面为准：[http://127.0.0.1:4173](http://127.0.0.1:4173)。关键规则如下：

1. 输入框“发送”和流程栏“下一步”执行同一个当前步骤；发送会先追加补充信息，下一步不追加文字。
2. 当前步骤、生成目标和完成状态必须同时可见；步骤完成卡提供打开、撤回、重试和下一步。
3. 校验步骤额外提供“通过”；正文完成卡额外提供“草稿”和“评分”。
4. 已有目标文件时不得直接静默覆盖，必须让用户选择查看、覆盖或跳过。
5. 删除项目、章节和文件前必须二次确认；项目删除会递归删除该项目全部本地文件，当前无回收站。
6. 右侧结构化编辑只用于支持的 JSON / Markdown 资产；配置步骤优先使用受控选项面板。
7. 模型不可用时保留输入和进度，并引导用户进入设置。
8. 生成上下文在应用层不做静默截断；超过请求、文件或模型上下文上限时应明确失败。聊天界面快照超过约 1.8 MB 时会移除最早消息，但不影响已落盘正式资产。

### 4.4 产品原则

- 单步单产物：每一步只解决一个明确问题；
- 关键事实先判别：资料不足时先补充，不直接生成正式资产；
- 用户输入持续累积：初始化与每章分别保存原始信息；
- 正式产物文件化：结构化源与可读版分离；
- 失败不覆盖：校验通过前不以失败结果替换正式文件；
- 用户最终确认：自动模式可以推进，但在缺输入、冲突或完成节点暂停；
- 边界显式：本地存储不等于完全离线，调用外部模型时内容会发送给所选提供方。

## 5. 功能需求

以下需求默认使用角色为“当前设备上的项目作者”。除特别说明外，用户已启动本地服务并选择一个有效项目；所有项目数据只能读写 `小说项目/<项目名>/` 内部路径。当前没有账号或角色权限，同一操作系统用户下能访问本地工作台的人拥有全部项目读写权限。

| FR-106 | 更新全局资产 | 顶部“可更新”包含简介、世界观、语言风格、角色名单、角色卡、关系卡、信息账本、剧情书；用户选择目标并补充要求后调用对应任务 | P1 | 目标在输入框上方可见且可取消；成功后刷新对应文件；已有文件先触发查看 / 覆盖 / 跳过选择 |

#### 5.2.1 初始化步骤契约

### 5.3 章节生成与验收

| --- | --- | --- | --- | --- |
| FR-201 | 新建、切换、重命名和删除章节 | 初始化完成后才进入章节流程；删除章节同时删除其正文与提示词目录，且需二次确认 | P0 | 章节操作后导航、正文路径和提示词目录保持一致；删除不影响其他章节 |
| FR-202 | 判别章节原始信息 | 至少包含一名已知角色和具体剧情 / 因果推进；补充内容持续追加到本章独立文件 | P0 | 信息不足时不生成锚点；通过后写入 `运行记录/章节输入/<章节>.md`，下游读取完整累积信息 |

| FR-205 | 生成关键台词 | 读取锚点、角色 / 关系卡、语言风格和对话词库 | P1 | 台词使用规定结构并同时生成 JSON + Markdown；缺角色或台词输入时拒绝 |

| FR-207 | 生成正文 | 仅在快照完成后调用所选模型；正文非空即可落盘，格式和语义集中留给后续校验 | P0 | 快照缺失时不得生成；成功写入对应卷 / 章节 TXT；失败不产生空正文或覆盖旧正文 |

### 5.4 流程控制、模型与失败处理

| 编号 | 功能与正常流程 | 规则、异常与数据 | 优先级 | 验收标准 |
| --- | --- | --- | --- | --- |
| FR-301 | 标准模式 | 用户用自然语言补充当前步骤，生成后手动决定下一步 | P0 | 发送与下一步执行同一当前任务；结果卡动作可用 |
| FR-302 | 自动模式 | 步骤成功后继续下一个启用步骤 | P1 | 遇到缺输入、已有文件冲突、失败或流程结束时暂停；不得绕过门禁 |
| FR-303 | 手动模式 | 对已支持资产使用结构化编辑和选择面板 | P2 | 当前仅标记为部分可用；未支持步骤不得宣称完整手动模式 |
| FR-304 | 撤回、重试、跳过、取消和已有文件处理 | 重试沿用当前步骤输入；可选步骤允许跳过；运行任务可取消；已有文件必须显式选择 | P0 | 操作后步骤索引、输入和正式文件状态一致；同一 `runId` 不得并发复用 |

| FR-306 | 自动重试与失败卡 | 429、500、502、503、504 和瞬时网络错误最多尝试 3 次并退避；4xx 参数错误不自动重试 | P0 | 失败卡显示步骤、错误和已有用量；正式产物不被失败结果覆盖；用量写入执行记录 |

## 6. 非功能需求

### 6.1 性能与容量

| 编号 | 要求 | 当前实现 / 验收口径 |
| --- | --- | --- |
| NFR-001 | 普通项目、文件和设置操作应在本机 2 秒内给出结果或加载状态 | 待建立性能脚本；不得因模型调用阻塞整个页面 |
| NFR-002 | 模型步骤必须显示进行中状态并允许取消 | 单次 LLM 请求默认超时 180 秒，工作流进程总超时 30 分钟 |
| NFR-003 | 支持长输入且不得静默截断生成上下文 | HTTP 请求体上限约 30 MB，上传上限 20 MB，文本写入上限 2 MB；超限必须明确报错；外部模型上下文上限由提供方决定 |
| NFR-004 | 对话恢复文件不得无限增长 | 界面快照约 1.8 MB 后移除最早消息；正式资产与执行日志不受此裁剪影响 |

### 6.2 安全与隐私

| 编号 | 要求 | 当前实现 / 已知差距 |
| --- | --- | --- |
| NFR-005 | 本地服务只接受回环地址和本地页面来源 | 校验 Host / Origin，拒绝外部来源和 DNS rebinding 风险请求 |
| NFR-006 | 文件操作不得越出当前项目目录 | 项目名、文件名和相对路径均做安全校验；测试覆盖路径穿越 |
| NFR-007 | 静态服务只暴露必要前端文件 | 仅白名单提供 HTML、CSS、JS，不暴露服务端 `.mjs` 等文件 |
| NFR-008 | 删除操作必须可感知 | UI 二次确认；当前为永久删除，无回收站和自动备份，属于已知风险 |
| NFR-009 | API 密钥不得进入小说资产、日志和作品展示 | 当前密钥保存在本机 `工作流脚本/工作台设置.json` 并通过环境变量传给子进程；尚未使用系统密钥链或加密存储，禁止提交或分享该设置文件 |
| NFR-010 | 明示外部模型的数据边界 | 小说资料和生成上下文会发送至用户选择的模型提供方；产品“本地”仅指界面、流程和资产存储，不代表模型推理完全离线 |

### 6.3 可用性、兼容性与稳定性

- 主要目标为 Windows 桌面端 Chromium 浏览器；Node.js 18+、Python 3.11 / 3.12。macOS、Linux 和其他浏览器仅有启动脚本，尚未完成系统兼容性验收。
- 所有失败必须给出用户可执行的下一步，如补充资料、配置模型、查看详情或重试，不显示无解释的空白状态。
- 页面关键按钮应具备可读标签、焦点入口和键盘可操作性；完整无障碍审计尚未完成。
- 程序刷新或模型失败不得破坏已落盘资产；项目状态可从磁盘恢复。
- JSON 模型返回兼容代码围栏和前后说明文字，但解析失败必须明确报错，不猜测错误结构。

## 7. 数据与度量

### 7.1 数据定义与存储

| 数据 | 存储位置 | 用途 | 保留规则 |
| --- | --- | --- | --- |
| 项目正式资产 | `小说项目/<类型>-<名称>/` 下的知识库、剧情、提示词、正文等 | 生成上下文与用户交付物 | 随项目永久保留，直到用户删除 |
| 流程状态 | `运行记录/workflow-state.json` | 恢复初始化、章节、步骤和累计用量 | 随项目保留 |
| 原始用户信息 | `初始化资料.md`、`章节输入/*.md` | 下游步骤完整上下文 | 随项目保留 |
| 执行记录 | `运行记录/执行记录/*.jsonl` | 模型、token、耗时、成功 / 失败审计 | 随项目保留 |
| 对话快照 | `运行记录/对话记录.md` | 刷新后恢复中间对话 | 超过约 1.8 MB 时裁剪最早界面消息 |
| 模型设置与密钥 | `工作流脚本/工作台设置.json` | 提供方与分步骤模型配置 | 工作区级长期保留；当前为明文风险 |

固定格式资产采用双文件：JSON 是程序读写的结构化源，Markdown 是用户查看和编辑的可读版。正文、草稿使用 TXT，评分和报告使用 Markdown / JSON。

### 7.2 用量口径

- `prompt_tokens`：提供方返回的输入 token；
- `completion_tokens`：提供方返回的输出 token；
- `total_tokens`：两者之和；
- `response_time`：每次模型请求的响应时间之和；
- `calls`：记录到的模型调用次数，重试会形成独立执行事实；
- 项目顶部“总输入 / 总输出”来自当前状态，并可从成功执行日志回填历史值；提供方不返回 usage 时显示值可能为 0。

### 7.3 事件与后续埋点

当前无远程埋点，避免在未说明的情况下上传创作行为。若进入用户验证，可优先增加仅本地聚合、由用户主动导出的事件：

| 事件 | 关键属性 | 用途 |
| --- | --- | --- |
| `project_created` | 类型、是否复制默认资产 | 入口转化 |
| `step_started / completed / failed` | 流程、步骤、模式、耗时、错误类型 | 漏斗与失败定位 |
| `step_retried / undone / skipped` | 步骤、原因 | 返工成本 |
| `workflow_restored` | 恢复节点、是否成功 | 恢复能力 |
| `chapter_approved` | 章节、校验结论、重试次数 | 核心完成率 |

任何对外遥测都必须另行征得用户同意，并默认不上传正文、提示词、密钥和原著内容。

## 9. 发布与过渡要求

### 9.1 发布范围

- 发布形态：本地源码 / 文件夹，一键启动本地服务；
- 支持环境：优先 Windows 桌面端；
- 数据范围：只操作 `小说项目/`、默认资料和工作台设置；
- 默认不调用真实模型测试，只有显式传入 `--live-model` 才会消耗 API 额度。

### 9.2 上线前验收条件

1. `PYTHONUTF8=1` 环境下运行 `python 工作流脚本/运行测试.py --suite 全部`，五个套件全部通过；
2. 使用计划支持的真实模型至少完成一次“资料判别 → 初始化 → 首章正文 → 校验”的端到端验收；
3. 仓库和作品展示中不包含有效 API 密钥、原著私密文本或测试用户数据；
4. 新建、重命名、删除、恢复和已有文件冲突流程完成实机检查；
5. README、PRD、技术文档和可运行界面中的功能状态一致。

### 9.3 迁移、回滚与用户通知

- 不提供自动迁移接口：旧项目保持扁平布局即可继续使用；需要分卷时用户自行整理文件夹（正文/提示词同步移动）；
- 版本回滚只回滚程序代码，不应覆盖用户的 `小说项目/` 和本机设置；
- 当前没有自动数据库迁移和回收站，涉及目录结构变化时必须先复制备份并提供迁移结果清单；
- 发布说明必须列出新增 / 移除步骤、文件结构变化、模型调用变化和已知风险。
